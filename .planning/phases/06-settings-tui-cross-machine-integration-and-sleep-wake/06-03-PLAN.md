  <action>
    The SSH agent forwarding issue has two parts: (A) sbx needs to know the host SSH_AUTH_SOCK path so it can set up the relay socket, and (B) the kit must start a socat relay inside the sandbox bridging the sbx-provided relay socket to the well-known /run/ssh-agent.sock path.

    Part A: In src/containers/sbx/mod.rs create_container, after materializing the kit and before calling Command::new, check if the host has SSH_AUTH_SOCK set via std::env::var("SSH_AUTH_SOCK"). If present, add it to the Command environment via cmd.env("SSH_AUTH_SOCK", &host_sock_path). This tells the sbx daemon where to find the host agent socket so it can create a relay. The spec.yaml credentials.sources.ssh.env already declares SSH_AUTH_SOCK as a credential source, which tells sbx to relay it; but the daemon needs the actual path from the calling process's environment.

    Additionally, in build_create_args (argv.rs), add a new parameter ssh_auth_sock: Option<&str>. When Some(path), emit -e SSH_AUTH_SOCK=<path> BEFORE the sandbox name/paths in the args vec (after the --template and resource args but before positional paths). Update all call sites of build_create_args (there are two: the one in create_container at mod.rs:122, and the one in runtime.rs build_create_args dispatch). For the runtime.rs call site, pass None (that code path is for the string-formatting case, not the actual create). For the create_container call in mod.rs, pass the resolved SSH_AUTH_SOCK value.

    Part B: In src/containers/sbx_kit/spec.yaml, add a startup command that starts the socat relay if /run/ssh-agent.sock exists but is not already functioning. The startup command goes in the commands.startup array (after the existing agent binary check). The command should be:
    ["sh", "-c", "[ -S /run/ssh-agent.sock ] || exit 0; ssh-add -l >/dev/null 2>&1 && exit 0; exit 0"]

    Actually, the correct approach for sbx SSH relay: the spec.yaml credentials.sources.ssh.env declaration tells sbx to make SSH_AUTH_SOCK available inside the sandbox. The relay is handled by the sbx daemon itself (it creates the socket at /run/ssh-agent.sock). The issue is that the sbx daemon needs the host-side SSH_AUTH_SOCK path in its process environment at create time to set up the relay. So Part A (passing the env var) is the real fix. Part B should instead verify the relay is operational with a startup check that sets SSH_AUTH_SOCK=/run/ssh-agent.sock if not already set, since the agent binary needs this env var pointing to the relay socket.

    Update spec.yaml: add a startup entry before the agent-binary-check: ["sh", "-c", "export SSH_AUTH_SOCK=/run/ssh-agent.sock; [ -S \"$SSH_AUTH_SOCK\" ] && ssh-add -l >/dev/null 2>&1 || true"]

    This ensures that (1) the env var is set correctly inside the sandbox and (2) the relay is probed at startup (logging any issue without failing).

    Update the existing argv tests: add a test create_args_with_ssh_auth_sock that passes ssh_auth_sock=Some("/tmp/agent.sock") and asserts -e SSH_AUTH_SOCK=/tmp/agent.sock appears in the output. Add a test create_args_without_ssh_auth_sock that passes None and asserts no SSH_AUTH_SOCK in output.
  </action>
