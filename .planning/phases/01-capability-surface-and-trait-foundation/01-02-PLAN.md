<threat_model>
## Trust Boundaries

This plan adds a 4th runtime variant whose every method returns a stub. The only externally observable behavior change is that `ContainerRuntimeName::Sbx` is now a deserializable config value. There are two boundaries worth naming:

| Boundary | Description |
|----------|-------------|
| TOML config file ↔ `ContainerRuntimeName` deserializer | A user (or a malicious config writer with file-system access) can write `container_runtime = "sbx"` into the SandboxConfig. Phase 1 stub returns `is_available() == false`, so the worst case is "user picks sbx, sees a runtime-not-available message, picks something else". No subprocess invocation occurs. |
| `PATH` lookup (Phase 2 concern, surfaced here) | If a user installs a binary named `sbx` on `PATH` between Phase 1 and Phase 2, Phase 1's `is_available()` short-circuit ensures aoe never invokes it, regardless of what the binary actually does. This is the "cannot be tricked into returning true via env var or PATH manipulation" requirement from the planning context's threat-model hint. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-05 | Spoofing | A binary named `sbx` on `PATH` impersonating Docker Sandboxes | mitigate | Task 2 short-circuits `ContainerRuntime::sbx().is_available()` to `false` unconditionally via the `match self.kind { RuntimeKind::Sbx => false, ... }` impl. No `--version` probe is performed; the spoof binary cannot influence aoe's behavior in Phase 1. Verified by `test_sbx_is_available_returns_false_unconditionally` plus the structural `grep -A1 "RuntimeKind::Sbx =>"` gate that proves the arm body is a literal `false` (no delegation to `self.base.is_available()`). Phase 2 (RT-02) introduces `which sbx` probing with the typed `SbxNotConfigured` error path; that's where this threat re-enters scope. |
| T-01-06 | Tampering | TOML config writes `container_runtime = "sbx"` | accept | Serde deserializes the value unchanged; downstream factory returns a stub runtime; `is_available()` returns false; the existing UI / CLI surfaces will display "runtime unavailable" the same way they would for any uninstalled runtime. No new attack surface beyond what Docker / Podman / AppleContainer already expose. |
| T-01-07 | Information Disclosure | The placeholder `exec_command` arm returns a string `format!("sbx exec {}", name)` | accept | The string is unreachable in normal flows because `is_available()` returns false. If a future caller bypasses the availability check, the worst case is leaking the container `name` (which is already a public identifier). No secret material is interpolated. |
| T-01-08 | Denial of Service | Stub arms returning `Ok(false)` / empty `HashMap` | accept | All stubs are constant-time, no allocation beyond `String::new` / `HashMap::new`. Cannot be made to consume resources. |
| T-01-09 | Elevation of Privilege | New attack surface from the Sbx variant | accept | No subprocess invocation, no file I/O, no network, no parsing of external input beyond the existing serde TOML path that already handles 3 sibling variants. |

No HIGH-severity items. No package installs in this plan; package-legitimacy gate not applicable.
